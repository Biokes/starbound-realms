# Mainnet Migration Plan

This document covers what changes between testnet and mainnet for Starbound Realms: admin key custody, the asset issuance process for IRON/NRGY/PLSM, and the rollback/pause plan if something goes wrong after launch.

Linked from the [README Roadmap](../README.md#roadmap).

---

## Admin Key Custody

### Current state (testnet)

Each contract stores a single `admin` address in instance storage. On testnet this is a funded keypair generated by `setup-testnet.sh`, kept in `.env.testnet`. Losing it is recoverable — testnet state is ephemeral.

### Mainnet requirement

On mainnet, the `resources` contract admin is also the SAC (Stellar Asset Contract) admin for IRON, NRGY, and PLSM. Compromising or losing it means losing the ability to mint resources and, more critically, losing control of three live Stellar assets. This is unrecoverable without a network-level intervention.

### Plan

Use a **Stellar multi-signature account** as the admin address for all four contracts before mainnet deployment.

Soroban's `require_auth` works natively against multi-sig Stellar accounts — no custom threshold logic is needed in the contracts. The account's signing thresholds should be configured as follows:

| Operation | Threshold |
|---|---|
| General (day-to-day admin) | 2-of-3 signers |
| High (asset admin changes, contract upgrades) | 3-of-3 signers |

**Signer custody:**
- Signer A: hardware wallet held by core maintainer 1
- Signer B: hardware wallet held by core maintainer 2
- Signer C: paper/offline backup stored in a physically separate location

No signer key should ever be stored in a `.env` file, CI secret, or cloud service on mainnet.

The multi-sig account itself becomes the `admin` passed to each `initialize` call at deployment time. Issue #224 tracks adding explicit n-of-m threshold enforcement at the contract level as an additional safety layer.

## Asset Issuance Process

### What needs to happen

IRON (`IRON`), Energy (`NRGY`), and Plasma (`PLSM`) must be issued as real Stellar classic assets on mainnet. The process:

1. **Create the issuer account.** This is the multi-sig admin account. Fund it with the minimum XLM reserve.

2. **Register the three Stellar Asset Contracts (SACs).** Run `stellar contract asset deploy` for each of the three asset codes, specifying the issuer account. Record the three resulting contract addresses.

3. **Transfer SAC admin to the resources contract.** After deploying the resources contract, call `set_admin` on each SAC to hand admin rights to the resources contract address. This is the same step `setup-testnet.sh` performs and is required for `mine` to work. After this point, the multi-sig account can no longer unilaterally mint — all minting goes through the resources contract.

4. **Players establish trustlines.** The frontend guides players through a one-time trustline setup on first login (already implemented via `OnboardingModal`).

5. **Initial mint.** After trustlines are in place, the admin may call `resources.mint` to seed any bootstrap balances needed for the game launch (e.g., tutorial rewards). All subsequent minting happens via `mine`.

### No test tokens on mainnet

Testnet IRON/NRGY/PLSM balances do not carry over. Players start from zero.

## Rollback and Pause Plan

### Emergency pause

All four contracts now implement `pause` / `unpause` (added in issue #223). In a live incident:

1. The admin multi-sig calls `pause(admin)` on the affected contract(s).
2. All state-mutating functions reject with `"contract is paused"`.
3. Read-only functions (`get_system`, `balance`, `get_fleet`, `get_battle`) remain available so the backend indexer and frontend can still display state.
4. Once the issue is diagnosed and a fix deployed (or confirmed not needed), the admin calls `unpause(admin)`.

The pause must be exercised on testnet before mainnet launch to verify the multi-sig signing flow works end-to-end.

### Contract upgrades

Soroban supports WASM upgrades via `update_current_contract_wasm`. An upgrade function should be added to each contract (admin-gated) before mainnet launch. Until then, an upgrade requires redeployment and re-initialization, which is destructive to on-chain state.

If a critical bug is found post-launch before an upgrade path exists:
1. Pause the affected contract immediately.
2. Announce the pause publicly with a brief explanation.
3. Assess whether a re-deployment with migrated state is feasible or whether a rollback to a previous ledger sequence is necessary (the latter requires coordination with Stellar validators and is a last resort).

### Monitoring

The backend indexer polls Soroban RPC for contract events. A health dashboard or alerting rule (e.g., on the battle contract emitting an unusually high rate of `battle_resolved` events, or the resources contract minting far above baseline) should be in place before mainnet launch to detect anomalies early.
